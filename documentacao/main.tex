\section{Introdução}

O crescimento contínuo da prática de atividades físicas no Brasil, evidenciado pelos
dados da Sociedade Brasileira de Endocrinologia e Metabologia (SBEM)\footnote{SOCIEDADE BRASILEIRA DE ENDOCRINOLOGIA E METABOLOGIA (SBEM). \textit{Dados sobre a prática de atividade física no Brasil}. [link oficial e ano da pesquisa --- campo editável, a ser preenchido com a fonte efetivamente consultada].}, impulsiona a
demanda por soluções digitais capazes de organizar e acompanhar a evolução de treinos de
forma estruturada. Assim, o \textbf{RepMax} surge como uma plataforma web voltada ao registro
de treinos de musculação, à visualização de progresso e à integração entre alunos e
personal trainers, somando mais tecnologia ao meio fitness.


\subsection{Problema de Negócio}

Observam-se, entre praticantes de musculação, as seguintes dificuldades recorrentes:

\begin{itemize}
    \item Ausência de um histórico organizado de séries, repetições e cargas utilizadas em cada treino;
    \item Dificuldade de identificar se um exercício está em progressão, estagnação ou regressão de desempenho;
    \item Falta de suporte para técnicas de intensificação de treino (bi-set, tri-set, monster set e drop set), que hoje são anotadas de forma manual e pouco estruturada;
    \item Dúvidas frequentes sobre a execução correta de determinados exercícios, sem uma referência disponível no momento do treino;
    \item Ausência de um canal integrado entre aluno e personal trainer, que hoje depende de aplicativos de mensagens externos (como WhatsApp) e planilhas avulsas.
\end{itemize}

\subsection{Proposta do Trabalho}
Embora esse projeto tenha como objetivo principal resolver o problema de negócio e agragar valor para o cliente, há também o propósito de aprendizado de conceitos. Por isso, esse trabalho propõe o desenvolvimento de uma API RESTful para um sistema de log book de treino, denominado \textbf{RepMax}. E uma interface WEB usando: React + Typescript + Tailwind CSS + React Router (\textbf{Data Mode}) + Vite + fetch() para interagir com ela (Mais abaixo tem a justificativa para o uso de cada parte da interface). A solução tem como objetivo permitir que o usuário registre seus treinos de forma estruturada, acompanhe sua progressão por meio de indicadores, tais como: a repetição máxima estimada (1RM),  técnicas avançadas de intensidade e, em uma segunda versão do sistema, viabilize a atuação de um personal trainer na montagem de treinos e no acompanhamento de alunos.

\section{Descrição Geral do Sistema}

\subsection{API RESTful}

Ela será responsável por gerenciar o histórico de treino de usuários. De forma geral, o sistema deverá permitir:

\begin{itemize}
    \item Cadastrar e autenticar usuários (alunos, personais e admins);
    \item Cadastrar exercícios, com grupo muscular e instruções de execução;
    \item Registrar treinos, associando exercícios, séries, repetições e cargas;
    \item Registrar séries em formatos de intensificação: bi-set, tri-set, monster set e drop set;
    \item Calcular a repetição máxima estimada (1RM) a partir de carga e repetições;
    \item Consultar o histórico e a evolução de desempenho por exercício;
    \item (Versão 2) Vincular aluno e personal trainer, permitindo que o personal monte treinos, o aluno registre feedback e ambos se comuniquem dentro do próprio sistema.
\end{itemize}

\subsection{Interface WEB:}
O conjunto de tecnologia (stack) foi escolhido para viabilizar o aprendizado de conceitos como: 
\begin{itemize}
    \item rotas;
    \item  cache;
    \item  segurança;
    \item  server-side;
    \item  client-side.
\end{itemize}

Cada parte da interface tem seu propósito:
\begin{itemize}
    \item Vite -> Ferramenta responsável pelo ambiente dev e processo de build do front-end
    \item React -> Biblioteca de UI, para construção e navegação na interface.
    \item Tailwind CSS -> Para estilização.
    \item React Router no modo Data -> Não faz mágica sozinho, mas traz ferramentas para eu aprender e usar como Rotas, Loader, Action e Estados de navegação.
    \item fetch() -> Para fazer requisição à API RESTful.
\end{itemize}

Esse conjunto permite que tenhamos um equilíbrio entre conceitos a aprender e aplicar e prazo de entrega. 

\subsection{Bloco: Treino Individual}

Concentra as funcionalidades de uso autônomo do aluno: cadastro de exercícios, registro de séries (incluindo as técnicas de intensidade), cálculo de 1RM, histórico e rotinas.

\subsection{Bloco: Acompanhamento por Personal Trainer}

Reúne as funcionalidades da segunda versão do sistema: vínculo entre aluno e personal, montagem de planos de treino pelo profissional, feedback do aluno e comunicação entre as partes.

\section{Estudo de Viabilidade}

\subsection{Viabilidade Técnica}

O sistema é tecnicamente viável em razão do uso de tecnologias consolidadas e amplamente adotadas no mercado de desenvolvimento de software:

\begin{itemize}
    \item Java, como linguagem de programação orientada a objetos;
    \item Spring Boot, para a criação simplificada da API;
    \item Spring Web, para a exposição dos endpoints HTTP;
    \item Spring Security, para segurança (JWT, Argon2);
    \item Spring Data JPA e Hibernate, para a camada de persistência de dados (ORM);
    \item PostgreSQL, como sistema gerenciador de banco de dados relacional;
    \item Maven, para o gerenciamento de dependências do projeto;
    \item Docker e Docker Compose, para padronizar o ambiente de execução.
\end{itemize}

A adoção da arquitetura em camadas (Controller, Service, Repository, Entity/DTO), detalhada na Seção 11, facilita a manutenção, os testes e a evolução futura do sistema, especialmente relevante dado o caráter incremental do projeto: a intenção declarada é iniciar com um escopo simples e evoluir gradualmente até um sistema completo.

\subsection{Viabilidade Operacional}

Do ponto de vista operacional, o sistema RepMax pode auxiliar diretamente os seguintes perfis de usuário:

\begin{itemize}
    \item \textbf{Alunos}, que passam a ter um histórico estruturado de treino e indicadores de progressão;
    \item \textbf{Personal trainers}, que passam a montar e acompanhar treinos de seus alunos diretamente pela plataforma;
    \item \textbf{Administradores}, responsáveis pela gestão geral de usuários e exercícios cadastrados no sistema.
\end{itemize}

\section{Atores do Sistema}

\subsection{Aluno}
Usuário final que utiliza o sistema para registrar seus próprios treinos. Pode: cadastrar exercícios e treinos, registrar séries, consultar seu histórico e progressão, criar rotinas, vincular-se a um personal trainer, visualizar planos de treino recebidos e enviar feedback.

\subsection{Personal Trainer}
Profissional vinculado a um ou mais alunos. Pode: aceitar vínculos de alunos, montar e editar planos de treino personalizados, visualizar o histórico e a evolução de cada aluno vinculado, receber feedbacks e se comunicar com os alunos via chat.

\subsection{Administrador}
Responsável pela gestão geral do sistema. Pode: gerenciar usuários, gerenciar o catálogo de exercícios e instruções de execução, e controlar permissões de acesso.

\section{Diagramas de Fluxo de Dados --- DFD}

\subsection{DFD de Contexto}
O sistema RepMax é representado como um processo único, interagindo com três atores externos (Aluno, Personal Trainer e Administrador) e com o banco de dados PostgreSQL. Os principais fluxos são: dados de cadastro e treino (Aluno \(\rightarrow\) Sistema), planos de treino montados (Personal \(\rightarrow\) Sistema \(\rightarrow\) Aluno), feedback e mensagens (Aluno \(\leftrightarrow\) Sistema \(\leftrightarrow\) Personal), operações de leitura/gravação junto ao banco de dados, e respostas da API para todos os atores.

\subsection{DFD de Registro de Treino}
\begin{enumerate}[label=\arabic*.]
    \item O aluno envia os dados do treino (exercícios, séries, repetições, carga, tipo de técnica).
    \item A API recebe e valida as informações.
    \item A camada Service aplica as regras de negócio (ex.: validar quantidade mínima de exercícios em um monster set).
    \item A camada Repository persiste os dados.
    \item O banco de dados PostgreSQL confirma a operação.
    \item A API retorna o treino registrado (TreinoResponseDTO), incluindo o 1RM estimado calculado.
\end{enumerate}

\subsection{DFD de Vínculo e Comunicação Personal-Aluno}
\begin{enumerate}[label=\arabic*.]
    \item O aluno solicita vínculo com um personal trainer.
    \item O personal recebe e aceita (ou recusa) a solicitação.
    \item O personal monta um plano de treino para o aluno vinculado.
    \item O sistema notifica o aluno sobre o novo plano.
    \item O aluno executa o treino e registra feedback.
    \item O sistema notifica o personal sobre o feedback recebido.
    \item Personal e aluno trocam mensagens via chat, persistidas no histórico de conversas.
\end{enumerate}

\textbf{Decisão de modelagem --- Técnicas combinadas:} bi-set, tri-set e monster set são modelados como múltiplas instâncias de \texttt{SerieExecutada} compartilhando o mesmo \texttt{grupoSequencia} e \texttt{tipoTecnica}, em vez de criar uma entidade separada para cada técnica. Essa decisão simplifica o modelo relacional e permite reaproveitar a mesma tabela para séries normais e combinadas, com a camada de Service validando a quantidade mínima de exercícios exigida por tipo (2 para bi-set, 3 para tri-set, 4+ para monster set).

\textbf{Exemplo detalhado --- UC02 (Registrar treino com bi-set):}
\begin{description}[leftmargin=1.2cm]
    \item[Objetivo:] Registrar uma sessão de treino contendo uma combinação de bi-set.
    \item[Pré-condições:] O aluno deve estar autenticado; os exercícios envolvidos devem estar previamente cadastrados.
    \item[Fluxo principal:] (1) o aluno informa os dois exercícios do bi-set, com suas respectivas repetições e cargas; (2) o sistema valida que há exatamente dois exercícios associados ao mesmo \texttt{grupoSequencia}; (3) o sistema persiste as séries com \texttt{tipoTecnica = BI\_SET}; (4) o sistema retorna o treino registrado, incluindo o 1RM estimado de cada exercício.
    \item[Fluxo alternativo:] Caso apenas um exercício seja informado para um bi-set, o sistema rejeita o registro e retorna erro de validação (RNF12).
\end{description}

\section{Arquitetura da Aplicação}

O RepMax adota a arquitetura em camadas (Controller, Service, Repository, Entity), amplamente utilizada em aplicações Spring Boot, complementada pelo uso de DTOs.

\begin{itemize}
    \item \textbf{Controller:} recebe as requisições HTTP, realiza validação básica e delega à camada de Service, retornando DTOs de resposta.
    \item \textbf{Service:} concentra as regras de negócio --- cálculo de 1RM, validação de técnicas combinadas (bi-set/tri-set/monster set/drop set), regras de vínculo aluno-personal.
    \item \textbf{Repository:} acessa o PostgreSQL via Spring Data JPA, com consultas personalizadas para histórico e progressão.
    \item \textbf{Entity:} representa as tabelas do banco descritas na Seção 9, mapeando os relacionamentos com anotações JPA (\texttt{@OneToMany}, \texttt{@ManyToOne}, \texttt{@OneToOne}).
    \item \textbf{DTO:} evita a exposição direta das entidades, com exemplos como \texttt{TreinoRequestDTO}, \texttt{TreinoResponseDTO}, \texttt{SerieExecutadaDTO}, \texttt{ProgressoDTO} e \texttt{PlanoTreinoDTO}.
\end{itemize}

\section{Regras de Negócio}

\begin{enumerate}[label=\arabic*.]
    \item A carga registrada em uma série não pode ser negativa; o número de repetições deve ser maior que zero.
    \item Um bi-set deve conter exatamente dois exercícios distintos no mesmo \texttt{grupoSequencia}; um tri-set, exatamente três; um monster set, quatro ou mais.
    \item Em um drop set, a carga de cada série subsequente deve ser estritamente menor que a da série anterior dentro do mesmo exercício.
    \item O cálculo de 1RM deve utilizar a fórmula de Epley e ser restrito a séries com até 10--12 repetições, faixa em que a fórmula mantém boa precisão.
    \item Um vínculo entre aluno e personal só é efetivado mediante aceite explícito do personal.
    \item Um plano de treino só pode ser criado ou editado pelo personal vinculado ao aluno correspondente.
    \item Um aluno não pode acessar o histórico ou os planos de treino de outro aluno, salvo o personal, que acessa apenas os dados dos alunos a ele vinculados.
    \item O sistema deve impedir a criação de séries, feedbacks ou mensagens vinculados a treinos ou usuários inexistentes.
    \item Alertas e sugestões do sistema (ex.: progresso estagnado) têm caráter informativo e não substituem a orientação de um profissional de educação física.
\end{enumerate}

\section{Segurança e Privacidade}

\begin{itemize}
    \item \textbf{Autenticação:} obrigatória para acesso a qualquer recurso protegido da API (JWT).
    \item \textbf{Autorização por perfil (RBAC):} aluno, personal trainer e administrador possuem permissões distintas.
    \item \textbf{Criptografia de senhas:} armazenamento via Argon2.
    \item \textbf{Validação de entrada:} todos os dados recebidos devem ser validados antes do processamento.
    \item \textbf{Proteção de dados entre usuários:} um aluno só acessa seus próprios dados; um personal só acessa dados de alunos vinculados e aceitos.
    \item \textbf{HTTPS em produção:} toda comunicação deve ocorrer de forma criptografada em um eventual ambiente de produção.
\end{itemize}

\section{Conclusão}

O sistema RepMax, apresentado ao longo desta documentação, propõe uma solução estruturada para o registro e acompanhamento de treinos de musculação, contemplando desde funcionalidades básicas de um log book até técnicas avançadas de intensidade (bi-set, tri-set, monster set e drop set) e um modelo colaborativo entre aluno e personal trainer. O projeto foi concebido de forma incremental, iniciando em um escopo simples e evoluindo em fases, o que permite consolidar conceitos de Java, Spring Boot e persistência com JPA/PostgreSQL ao longo do desenvolvimento.

Reforça-se que, no momento desta entrega, nenhuma das funcionalidades apresentadas foi implementada: este documento reflete integralmente a fase de análise e especificação do projeto, servindo de base para as etapas subsequentes de implementação.
